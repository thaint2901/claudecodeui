# Capability: Edit Sent Prompt (Conversation Fork)

## Description

Lets the user edit a prompt they already sent and re-send it, forking the conversation in place at that point rather than appending a correction turn. The fork is implemented on top of the Claude Agent SDK's own resume mechanics (`resume` + `resumeSessionAt` + `forkSession`), so the branch is a first-class Claude session with its own transcript — cloudcli does not hand-edit JSONL. Only Claude sessions support this; Cursor, Codex, and OpenCode have no equivalent resume-at-message primitive.

Code changes made by the tool calls in the original branch are **never reverted** by a fork. Forking only rewinds the *conversation* the model sees; if the user wants to undo file edits, that is a Git operation via the Git panel, not part of this feature.

## Actors

- **End-user developer** — Clicks Edit on a previously sent prompt, changes its text, and re-sends it.
- **`MessageComponent`** — Renders the Edit control (pencil icon plus an "Edit" label) on eligible user turns and calls back into the composer. The control sits in a row *below* the prompt bubble, alongside copy, the version pager and the timestamp, and fades in on hover. Two escapes keep hover-gating from stranding anyone, both from shared rules in `src/index.css`: a coarse pointer (no hover to give) pins the row visible, and `:focus-within` reveals it for keyboard users. The timestamp in that row is *not* gated — it stays visible at rest, matching assistant turns.
- **The composer (`useChatComposerState`)** — Loads the edited text into the input with a Git-note banner, and re-submits with `editAtMessageUuid` set.
- **`chat-websocket.service.ts`** — Validates the session is a Claude session with a transcript, locates the resume point, and dispatches the fork.
- **`findForkResumePoint`** (`claude-fork.provider.ts`) — Scans the session's JSONL transcript for the assistant-message uuid immediately preceding the edited user message.
- **Claude Agent SDK** — Performs the actual resume-and-fork via `resume` + `resumeSessionAt` + `forkSession`, producing a new provider session id and a new transcript file.
- **cloudcli SQLite (`sessions` table)** — Records the fork relationship (`fork_root_session_id`, `forked_from_session_id`, `forked_at_message_uuid`, `active_leaf`) so branches can be listed and switched without re-parsing every transcript.
- **`BranchSwitcher`** — Renders a pair of `‹ ›` chevrons with the position printed between them (`2/4`) once more than one branch exists. It belongs to the first user prompt *after* the fork anchor — the message that actually differs between siblings — not to the anchor itself, which every sibling shares verbatim. The printed counter is `aria-hidden` so a virtual-cursor user does not meet the position twice; the spoken version comes from a live region owned by `ChatInterface`.
- **`SidebarSessionItem`** — Shows one row per fork cluster (the active leaf). The row carries no branch affordance; branches are reached from the switcher on the forked prompt in the transcript.

## Trigger

- The user clicks the Edit control on a sent user-turn bubble in a Claude session that is not currently streaming.

## Flow

1. `canEditPrompt` (`provider === 'claude'`) gates whether the Edit control renders. It deliberately does *not* include `isProcessing`: that flag flips twice per message sent, and as a row prop it broke `React.memo` on every rendered message twice per send. Editing during a run is blocked at click time instead — `handleEditPrompt` reads `isProcessingRef.current` and, rather than doing nothing, sets `forkError` to `branch.editBlockedWhileRunning`, which the composer already renders through the shared `Alert`. So the control stays visible mid-run and says why it refuses. The conversation's FIRST user message never shows the icon (`firstUserMessageUuid` in `branchAnchors.ts`, pagination-aware): with no assistant turn before it there is no resume anchor, and the SDK would copy the full history instead of truncating.
2. Clicking Edit loads that message's text into the composer, along with the banner: *"Editing a sent prompt — the new branch only rewinds the conversation. Code changes after this point are kept (see the Git tab)."*
3. The user edits the text and sends. The composer includes `options.editAtMessageUuid` (the uuid of the message being edited) in the `chat.send` WS envelope, alongside the edited prompt text.
4. `chat-websocket.service.ts` rejects the request with a `protocol_error` (`code: 'FORK_FAILED'`) if the session isn't Claude, or has no transcript yet.
5. `findForkResumePoint` streams the transcript JSONL looking for the edited message's uuid, tracking the last-seen assistant uuid (`RESUME_POINT_RULE = 'preceding-assistant-uuid'`). It returns that assistant uuid as `resumeSessionAt`; a `null` result (edited message was the first prompt) is rejected with `FORK_FAILED` ("start a new session instead"), since omitting `resumeSessionAt` would copy the full history rather than truncate. Any other transcript problem also surfaces as `FORK_FAILED`.
6. The hub invokes `queryClaudeSDK` with `resume` (the original provider session id), `resumeSessionAt` (the resume point), and `forkSession: true`, plus the new prompt text.
7. The SDK creates a new provider session and transcript file that shares history up to the resume point, then continues with the edited prompt. During the new run, the old message tail is hidden client-side and the new prompt streams in its place.
8. **Mid-stream**, the instant the SDK announces the fork's provider session id, `recordProviderSessionId` records the fork edge in SQLite (`forked_from_session_id`, `forked_at_message_uuid`, `fork_root_session_id` propagated from the root), marks the new session `active_leaf = 1`, demotes the sibling, and emits `branch_created`. This is deliberately not deferred to `complete`, but *not* because the originating client adopts the branch early — it does not: `useChatRealtimeHandlers` only parks the branch id in `pendingBranchRef` when `branch_created` arrives and calls `onBranchCreated` on the run's `complete`. The early write buys three other things. **Durability:** the branch exists on disk the moment the SDK creates it, so a run that dies before `complete` still leaves a reachable session instead of an orphan transcript with no row. **Convergence:** the two `session_upserted` broadcasts fired alongside it reach every *other* tab immediately, so their sidebars move with the fork rather than at the end of the run. **Leaf correctness:** the cluster's active leaf points at the branch for the whole of the run, so anything reading the cluster mid-stream sees the branch that is actually being written. The consequence to keep in mind: a run that errors or is aborted *after* the id lands still leaves the branch row inserted and the cluster's active leaf already moved.
9. `useChatRealtimeHandlers` parks the branch id when `branch_created` arrives and hands it to `onBranchCreated` on the run's `complete` (including an aborted run — the branch row and transcript exist either way, so stranding the user on the parent view with its tail hidden would be worse). On a `FORK_FAILED` protocol error it invokes `onForkFailed` (`ChatInterface`), which restores the prior view, puts the edited text back in the composer and re-enters edit mode, and shows a destructive `Alert` above the input. The composer is cleared unconditionally at send time, so the submitted edit is held in a ref (`lastEditSubmissionRef`) specifically to survive that clear — without it a failed fork discarded the user's rewritten prompt with nothing on screen to say why.
   **Every one of these handlers is scoped to the session the event names**, not to the session on screen. Submitted forks are tracked per session id (`pendingForkRef`), and the recovery path only touches the composer when the failing session is the one in view. Unscoped, a fork failing in a *backgrounded* session cleared the viewed session's fork view, overwrote its composer with the other session's edited text and re-entered edit mode on a foreign message uuid — after which sending pushed that anchor against the wrong session. The mirror-image bug was a background run's terminal event injecting a fabricated fork error into whatever conversation happened to be on screen.
10. `BranchSwitcher` shows `‹ n/total ›` on the prompt that follows the fork anchor; either chevron calls `POST /sessions/:id/activate-branch` to switch which sibling is displayed, in place, without navigating away. Both ends stay focusable (`aria-disabled`, not `disabled`) so reaching the first or last version does not drop focus. A rejected activation is reported through the same composer `Alert` (`branch.switchFailed`) instead of leaving the chevron reading as a dead button.
    Switching destroys the pressed chevron's own React subtree — the pager lives in the prompt that *differs* between siblings — so focus and the announcement both have to be re-established by something that outlives the button. That something is a request-scoped controller, `useBranchSwitchController`. At press time (synchronously, before any await) it snapshots the anchor, the direction, the session in view, the input modality and the pager element. When the activation resolves it re-validates all of it: a switch that resolved after the user navigated elsewhere neither drags the route back nor takes focus, and focus is only reclaimed when the press came from the keyboard — restoring it after a *pointer* switch handed mouse users a `:focus-visible` ring the app never otherwise shows, because a programmatic `.focus()` on a fresh node counts as keyboard focus in Chrome.
    Focus restoration is a bounded per-frame sweep (1.5s deadline, stopping early once the arrow has held focus for five consecutive frames), not a claim consumed when the replacement pager mounts. The earlier claim-at-mount design is what shipped first and it failed in the browser: the transcript swap and the activation response race each other — measured, the remount landed anywhere from 50ms before to 250ms after the response — and when the remount won, the pager that would have claimed focus had already mounted and gone. The sweep also yields immediately if focus has moved somewhere the user put it.
    The live region lives on `ChatInterface`, outside the message list, so it survives the swap and is mutated in place — a region created together with its text is not reliably announced. Its text carries an invisible U+2060 WORD JOINER on alternating updates, because `useState` bails on an identical string: paging back to a position already announced left the DOM untouched and screen-reader users heard nothing while the whole transcript visibly changed. The controller empties the region on a session change (distinguishing "the user left" from "the switch we just announced landed"), so no conversation ever shows another's position.
    These are requirement-level statements and they are executable: `npm run a11y:branch -- --port=<app-port> --other-session=<id>` drives the pager over CDP against an already-open Chrome (`google-chrome --remote-debugging-port=9222`) and checks announcement-on-every-switch as real DOM mutations, keyboard vs. pointer focus behaviour, navigate-away safety, 20 consecutive keyboard switches with zero `<body>` landings, and the live region being empty after a session change. Like the perf gate it requires an explicit port and exits 2 as NOT MEASURED rather than reporting a pass it could not take.
11. `branch_created` goes only to the socket that started the run. Every *other* tab converges through the separate `session_upserted` broadcast, which is what moves their sidebar row — so a "my other tab did not update" report is a `session_upserted` problem, not a missed `branch_created` subscription.

## Output

- A new Claude session (new provider session id, new transcript file) that shares conversation history up to the resume point and diverges from there.
- Sidebar shows **one row per fork cluster** — the current active leaf — instead of one row per branch, and carries no branch-specific affordance.
- A pair of `‹ ›` chevrons with the position printed between them, rendered in the control row of the prompt that follows each fork anchor, and announced through a live region owned by `ChatInterface`.
- On failure: a `FORK_FAILED` protocol error, the original view left intact, the user's edited text restored into the composer with edit mode re-entered, and a destructive `Alert` naming the failure.

## Fork Graph Persistence

- Stored entirely in cloudcli's own SQLite `sessions` table (`server/modules/database/schema.ts`), not derived from transcripts at read time:
  - `fork_root_session_id TEXT` — the original, never-forked ancestor of the cluster.
  - `forked_from_session_id TEXT` — the immediate parent branch.
  - `forked_at_message_uuid TEXT` — the fork anchor: the uuid of the assistant message the branch resumed from. Unlike the edited user message's uuid (which exists only in the parent transcript), the anchor is copied into every sibling transcript, so the branch switcher can render in any branch. Always set for rows created by this flow (first-prompt edits, which would have no anchor, are rejected up front); the column stays nullable for schema simplicity.
  - `active_leaf BOOLEAN DEFAULT 1` — which sibling is currently displayed for the cluster; exactly one leaf per cluster is active. Deleting or archiving the active leaf promotes the most recently touched surviving sibling in the same transaction, and the sidebar query falls back to that same row if it ever meets a cluster with no leaf at all — without both, losing the leaf would hide the entire cluster, original conversation included.
- `GET /sessions/:sessionId/branches` returns all branches in a cluster (filtered to those whose transcript file still exists on disk).
- `POST /sessions/:sessionId/activate-branch` flips `active_leaf` to the given session and demotes its siblings.
- **Sessions forked outside cloudcli** (e.g. via `claude --resume` + manual `forkSession` from the CLI directly) have no row with these columns populated and simply appear as ordinary, unrelated sessions — cloudcli only builds the fork graph for forks it initiated itself.

## Dependencies

- **Chat & Agent Streaming** — The composer, message list, and WS envelope this feature extends.
- **Provider Integration** — Only the Claude provider implements resume-at-message; the capability is unavailable for Cursor, Codex, OpenCode.
- **Session Management** — The sessions-watcher and session list must tolerate multiple sibling sessions per cluster and surface only the active leaf.
- **Authentication & Security** — Branch REST routes are authenticated like all other session routes.
